# Harness AI Agent Skill

> **Version**: 2026.1  
> **Frameworks**: Python (FastAPI) | Go (Gin/Echo) | Rust (Axum/Actix) + React 19 

---

## 1. 愿景与目标

### 1.1 核心愿景

构建AI驱动的全栈工程体系，实现：

- **AI自主工程能力** - 让AI承担可自动化的代码审查、测试生成、部署决策等工程任务
- **人机协作开发流程** - AI提供建议和执行，人类进行关键决策和确认
- **多Agent协同工作** - 协调多个AI Agent协同处理复杂工程任务
- **可观测可审计** - 所有AI决策可追溯、可审计、可优化

### 1.2 Harness平台核心价值

本Skill深度融合Harness Engineering平台能力，Harness不仅是CI/CD工具，更是**AI Agent的基础设施底座**：

| Harness能力 | 对AI Agent的支撑 | 价值 |
|-------------|------------------|------|
| **Pipeline** | Agent执行编排器 | 标准化执行环境、声明式工作流 |
| **SRM** | Agent决策数据底座 | 实时指标、告警、健康状态 |
| **GitOps** | Agent配置管理 | 声明式配置、版本控制 |
| **STO** | 安全扫描结果 | 代码安全分析数据源 |
| **CCM** | 成本分析数据 | 资源优化决策支撑 |
| **Policy** | Agent行为约束 | OPA策略、RBAC权限控制 |
| **Approval** | 人工确认网关 | 关键操作强制审批 |

### 1.3 设计原则

1. **AI优先** - 优先让AI承担重复性、规则明确的工程任务
2. **人机协作** - AI建议，人类决策；关键操作必须人工确认
3. **渐进增强** - 从简单任务（代码审查）逐步扩展到复杂场景（故障自动处理）
4. **可观测性** - 所有AI决策需记录置信度、推理过程和执行结果
5. **技术中立** - 支持多种编程语言和框架，不绑定特定技术栈

### 2.2 非功能需求

#### NFR-001: 性能要求

- **代码审查响应时间** < 30秒（处理1000行代码）
- **部署风险评估响应时间** < 10秒
- **Agent编排任务调度延迟** < 1秒
- **故障诊断响应时间** < 15秒
- **智能测试生成响应时间** < 60秒（单个模块）

#### NFR-002: 可靠性要求

- **AI服务可用性** > 99.9%
- **人工确认系统可用性** > 99.99%
- **所有操作支持幂等重试**
- **任务执行失败自动重试**（最多3次）

#### NFR-003: 安全要求

- **AI决策置信度 < 0.85时必须人工确认**
- **生产环境变更强制人工审批**
- **敏感操作（数据删除、权限变更）需多级审批**
- **所有操作记录审计日志**（操作人、时间、结果、推理过程）
- **API通信使用TLS加密**

**置信度驱动的自动化分级策略**：

| 置信度范围 | 风险等级 | 执行策略 | Harness支撑 |
|------------|----------|----------|-------------|
| ≥ 0.95 | 低 | **自动执行** - AI自主完成，无需人工干预 | Pipeline自动编排 |
| 0.85 ~ 0.95 | 中 | **通知后执行** - 异步通知利益相关方，允许撤销窗口期（默认5分钟） | Approval Stage（自动通过） |
| < 0.85 | 高 | **强制确认** - 必须人工审批后才能执行 | Approval Stage（需审批） |
| 任意 | 关键操作 | **强制确认** - 生产部署、数据删除等关键操作无论置信度均需审批 | Approval Stage + Policy约束 |

#### NFR-004: 可观测性要求

- **所有AI决策记录置信度分数**
- **记录AI推理过程和决策依据**
- **支持决策结果的人工反馈**
- **提供AI决策准确率仪表盘**

## 3. 人机协作规范

### 3.1 必须人工确认的场景

以下场景**必须**触发人工确认流程：

1. **AI决策置信度 < 0.85**
2. **生产环境部署操作**
3. **自动回滚操作**
4. **数据库Schema变更**
5. **安全策略修改**
6. **成本优化建议涉及资源删除**
7. **跨服务依赖变更**

### 3.2 可AI自主执行的场景

以下场景**可以**由AI自主执行，无需人工确认：

1. **开发/测试环境代码审查**
2. **测试用例生成（置信度 > 0.9）**
3. **低风险配置变更（白名单内）**
4. **监控告警通知发送**
5. **文档自动生成**
6. **代码格式化建议**

### 3.3 审批流程要求

- **审批人配置** - 支持指定审批人列表
- **审批超时** - 默认24小时，可配置
- **自动升级** - 超时未审批自动升级至上级
- **通知渠道** - 支持Web、Slack、Email、Mobile
- **批量审批** - 支持相似操作的批量审批

### 5.4 自动化测试友好支持

为确保生成的代码能够无缝集成到自动化测试流程中，特别是包含Prewrite在内的测试工序，本Skill提供以下自动化测试友好支持规范：

#### 5.4.1 交互元素定位优化

- **test-data-id属性**: 为所有用户交互元素（按钮、输入框、下拉菜单等）添加唯一且语义化的`test-data-id`属性
- **命名规范**: `test-data-id`属性值需遵循"功能-组件-用途"的命名规范，例如：`login-button-submit`、`user-input-email`
- **唯一性保证**: 确保`test-data-id`属性值在整个应用范围内保持唯一性，避免重复或模糊不清的命名
- **语义化设计**: 命名应清晰反映元素的功能和用途，便于测试工具定位和理解

#### 5.4.2 数组类组件标记系统

- **aria-labels索引标记**: 对数组渲染的组件实现`aria-labels`索引标记系统，格式为"组件名称-索引值"
- **索引规则**: 索引值从0开始连续编号，与数组数据结构保持一致对应关系
- **示例格式**: 对于用户列表中的第i个用户，`aria-label`应为`user-item-0`、`user-item-1`等
- **辅助功能兼容**: 确保`aria-labels`同时符合无障碍访问标准

#### 5.4.3 代码结构要求

- **清晰的层次结构**: 生成的代码需保持清晰的层次结构，组件嵌套关系明确
- **容器边界**: 关键交互区域需设置明确的容器边界，便于测试工具进行区域划分和元素定位
- **模块化设计**: 采用模块化设计，便于测试工具进行组件级别的测试
- **可测试性优先**: 在代码设计中优先考虑可测试性，确保测试工具能够轻松访问和操作组件

#### 5.4.4 自动化测试友好性验证

- **测试属性检查**: 集成自动化测试友好性检查机制，验证所有关键交互控件均具备可被测试框架识别的定位属性
- **跨框架兼容性**: 确保生成的代码能够通过自动化测试工具的元素定位验证，包括但不限于Selenium、Cypress等主流测试框架
- **测试属性文档**: 提供测试属性文档，说明各交互元素的`test-data-id`属性值及其对应功能
- **验证流程**: 在代码生成后自动运行测试属性验证流程，确保所有要求的属性都已正确添加

#### 5.4.5 兼容性要求

- **W3C标准兼容**: 确保添加的测试属性符合W3C标准，不影响页面可访问性和正常功能
- **浏览器兼容性**: 保证测试属性在各主流浏览器环境下的一致性表现
- **性能影响**: 确保测试属性的添加不会对页面性能产生显著影响
- **向后兼容**: 确保测试属性的添加不会破坏现有功能和兼容性

## 8. 约束与限制

### 8.1 技术约束

- **LLM依赖** - 需要OpenAI/Anthropic API访问
- **Harness平台** - 部分功能需要Harness Enterprise订阅
- **网络要求** - 需要访问外部AI服务和Harness平台

### 8.2 能力边界

- **不能替代架构设计** - AI辅助但不替代人类架构决策
- **不能处理未知场景** - 对于未见过的故障类型，AI可能无法正确诊断
- **不能保证100%准确** - AI建议需人工确认，特别是高风险操作

### 8.3 合规要求

- **数据隐私** - 代码和日志数据需符合公司数据隐私政策
- **审计要求** - 所有AI决策需记录审计日志
- **安全合规** - 需通过安全团队的合规审查
